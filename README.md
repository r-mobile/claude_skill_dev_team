# Dev Automation Plugin

Полнофункциональный плагин для автоматизации цикла разработки мобильных приложений на Kotlin, Swift и Dart. Управляет всем процессом от анализа требований до финального тестирования с поддержкой параллельной разработки.

## Возможности

- 🎯 **Автоматический анализ требований** - преобразует простое описание в подробное ТЗ
- 🏗️ **Проектирование архитектуры** - создает масштабируемую архитектуру
- 👷 **Параллельная разработка** - управляет несколькими разработчиками одновременно
- 🔗 **Интеграция кода** - объединяет результаты разных разработчиков
- 👀 **Code Review** - проверяет качество кода
- 🧪 **Тестирование** - проверяет что приложение работает

## Поддерживаемые платформы

- **iOS** - Swift
- **Android** - Kotlin
- **Flutter** - Dart (кроссплатформа)

## 🔍 Context7 интеграция для актуальной документации

Плагин использует **Context7 MCP** для получения актуальной документации по:
- 📚 Официальная документация Kotlin, Swift, Dart
- 🏗️ Architecture patterns и best practices
- 📦 Библиотеки и фреймворки (последние версии)
- 🔒 Security best practices
- ⚡ Performance optimization
- 🐛 Deprecated подходы и миграции

**Какие skills используют Context7:**
- ✅ **Analyzer** - для актуальных требований платформ
- ✅ **Architect** - для современных архитектурных паттернов
- ✅ **Developer** - для документации при кодировании
- ✅ **Code-Reviewer** - для актуальных best practices

**Результат:** Код всегда соответствует современным стандартам и best practices

## Выбор режима работы

### 📊 Режим Standard (экономный) - рекомендуется для большинства проектов
- ✅ Баланс качество/цена
- ✅ Экономия 30-40% от максимальной стоимости
- ✅ Идеален для MVP и production приложений
- Все skills используют Sonnet/Haiku

### 👑 Режим Premium (максимальное качество) - для критичных проектов
- ✅ Максимальное качество анализа и архитектуры
- ✅ Opus для Analyzer, Architect, Code-Reviewer
- ❌ +50% стоимости
- ✅ Гарантированное quality для production-critical код
- Рекомендуется для финансовых, медицинских, HighLoad приложений

### Как выбрать?

**Standard режим если:**
- Разработка MVP или прототипа
- Стандартные мобильные приложения
- Бюджет ограничен
- Хороший баланс важен

**Premium режим если:**
- Production приложение с высокими требованиями
- Критичная архитектура (масштабируемость, security)
- Финансовые или healthcare данные
- Качество код критичнее стоимости

## Как использовать

### Выбор режима работы

**Шаг 1: Запусти Orchestrator skill**

Orchestrator сразу спросит:
```
Какой режим использовать?
📊 Standard (экономный) - рекомендуется
👑 Premium (максимальное качество)
```

**Выбери режим:**
- **Standard** - если нужен баланс цены и качества (по умолчанию)
- **Premium** - если нужно максимальное качество архитектуры и code review

### Быстрый старт

1. Запусти skill **Orchestrator**
2. Выбери режим (Standard/Premium)
3. Опиши что нужно разработать:
   ```
   Приложение для просмотра котов.
   Нужны экраны: список котов, детали кота, избранное.
   Платформа: Native (iOS + Android)
   ```
4. Orchestrator будет управлять всеми этапами разработки в выбранном режиме

### Пример процесса

```
Пользователь описывает задачу

    ↓

    ↓
Integrator объединяет код
    ↓
Code-Reviewer проверяет качество
    ↓

    ↓
Результат возвращается пользователю
```

## Документация по skills

### Orchestrator 🎯
Главный skill для управления разработкой. Запусти его первым с описанием задачи.

Основные действия:
- Уточняет требования у пользователя
- Управляет процессом разработки
- **🆕 Собирает вопросы** от разработчиков
- **🆕 Интерактивное взаимодействие** с пользователем во время разработки
- Координирует работу всех skills
- Представляет финальный результат

### Analyzer 📋
Создает подробное техническое задание из простого описания.

Выходные данные:
- Markdown ТЗ (для чтения)
- JSON ТЗ (для других skills)
- User stories
- Требования к архитектуре, API, безопасности, производительности, UI/UX

### Architect 🏗️
Проектирует архитектуру приложения на основе ТЗ.

Выходные данные:
- Диаграмма архитектуры
- Описание компонентов
- API контракты
- Data модели
- Интеграционные точки

### Dev-Lead 👔 (ГЛАВНЫЙ КООРДИНАТОР)
**ГЛАВНЫЙ МОМЕНТ**: Dev-Lead НЕ выполняет код сам, а только координирует!

Основные действия:
- **🆕 Рассчитывает оптимальное количество разработчиков (1-10)**
- Разбивает работу на задачи
- **🆕 Распределяет задачи между разработчиками с учетом зависимостей**
- Подготавливает фокусированные требования для каждого разработчика
- **🆕 Собирает вопросы** от разработчиков и передает их в Orchestrator
- Проводит code review готового кода
- **🆕 Делегирует исправления нужным разработчикам, не делает сам**

### Developer 💻 (ЗАПУСКАЕТСЯ N РАЗ ПАРАЛЛЕЛЬНО)
**🆕 N копий Developer skill работают одновременно (1-10)**

Процесс:
1. Получает свой набор задач от Dev-Lead (с учетом зависимостей)
2. Может спрашивать уточнения (вопросы идут через Dev-Lead → Orchestrator → пользователя)
3. Пишет код согласно требованиям
4. Может просить помощь у других разработчиков если есть пересечения
5. Выдает результат для интеграции

**ВАЖНО**: Каждый разработчик получает только свои задачи, не видит других!

### Integrator
Объединяет код от нескольких Developer skills в единое приложение.

Основные действия:
- Объединяет файлы в правильную структуру
- Выявляет и разрешает конфликты
- Проверяет что все компилируется
- Документирует изменения

### Code-Reviewer
Проводит детальный review объединенного кода.

Проверяет:
- Best practices для каждой платформы
- Соответствие архитектуре
- Безопасность кода
- Читаемость и документация
- Performance

### Tester
Проверяет что приложение работает.

Проверяет:
- Компиляция без ошибок
- Базовый функционал
- Обработка ошибок
- Performance
- Отсутствие crashes

## Управление процессом

### Уточнения во время разработки

На любом этапе ты можешь:
- Задать вопросы текущему skill'у
- Запросить уточнения
- Сделать правки в требованиях

### Параллельная разработка

Несколько Developer skills могут работать одновременно на независимых задачах. Task Orchestrator Agent управляет их координацией.

### Повторный запуск этапов

Если нужно переделать какой-то этап:
- Попроси Dev-Lead пересмотреть разбиение на задачи
- Попроси Developer переделать код
- Запусти Tester заново для проверки

## Требования к входным данным

### От пользователя:
- Описание того что нужно разработать
- Платформы (iOS, Android, Flutter или комбинация)
- Основной функционал
- Примерная сложность

Остальное уточнят skills (Analyzer и Dev-Lead).

## Выходные данные плагина

После завершения всех этапов получишь:
1. **Подробное ТЗ** - все требования структурированно
2. **Архитектурный дизайн** - как устроено приложение
3. **Разбивка на задачи** - что делал каждый разработчик
4. **Исходный код** - полное приложение (обычно в нескольких вариантах для разных платформ)
5. **Code Review отчет** - что проверено и найдено
6. **Тестовый отчет** - результаты тестирования

## Best Practices

### Для лучших результатов:

1. **Четкое описание** - чем подробнее опишешь что нужно, тем лучше результат
2. **Уточнения в процессе** - если что-то не понравилось, говори сразу
3. **Реалистичные сроки** - сложные приложения требуют больше времени
4. **Фокус на основном** - сначала основной функционал, потом nice-to-have

### Типичные ошибки:

❌ Слишком размытые требования - skills потратят время на уточнения
❌ Пытаться разработать слишком сложное за один раз - разбей на несколько этапов
❌ Игнорировать рекомендации skills - они опытны в мобильной разработке

## 🏗️ Архитектурные улучшения (v0.2.0)

### 1️⃣ State Machine для управления процессом

**Что это:** Явная машина состояний с четкими переходами, контрольными точками и возможностью отката.

**Состояния разработки:**
```
INIT → ANALYSIS → VALIDATION_ANALYSIS → ARCHITECTURE → VALIDATION_ARCHITECTURE
→ PLANNING → VALIDATION_PLANNING → INTERACTIVE_DEV → INTEGRATION → VALIDATION_INTEGRATION
→ REVIEW → VALIDATION_REVIEW → TESTING → VALIDATION_TESTING → DONE
```

**Преимущества:**
- ✅ Явный контроль над процессом (не магия)
- ✅ Контрольные точки для сохранения прогресса
- ✅ Возможность отката при ошибках
- ✅ Четкие критерии переходов между этапами
- ✅ Обработка ошибок на каждом этапе

**Реализация:**
- Каждый skill знает текущее состояние
- Validation фазы перед переходом (MUST_HAVE vs SHOULD_HAVE)
- Checkpoints для сохранения результатов
- Error Handler state для восстановления

### 2️⃣ Validation & Error Handling

**Что это:** Pre-validation фазы в каждом skill с явным определением критериев качества.

**Pre-validation в каждом skill:**

| Skill | Что проверяет | Если не валидно |
|-------|---------------|-----------------|
| **Analyzer** | ТЗ полное и структурированное | Переделать ТЗ |
| **Architect** | Архитектура четкая и детальная | Переделать архитектуру |
| **Dev-Lead** | План полный и распределение корректное | Переделать план |
| **Integrator** | Код компилируется и интегрируется | Переделать интеграцию |

**MUST_HAVE vs SHOULD_HAVE критерии:**
- **MUST_HAVE**: блокирующие (если не соответствует → процесс не продолжается)
- **SHOULD_HAVE**: рекомендации (если не соответствует → warning но продолжает)

**Error Handling:**
- RECOVERABLE ошибки → retry или rollback
- CRITICAL ошибки → stop и report пользователю
- WARNING ошибки → log и continue

### 3️⃣ Performance Optimization

**Что это:** Три основные оптимизации для быстроты и эффективности.

#### 3.1 Минимизация контекста для Developer

**Problem:** Developer получал 100KB+ контекста (полное ТЗ + архитектуру + все требования).

**Solution:** Developer получает ТОЛЬКО свою задачу (5-10KB).
```
Было: Developer видит все (запутанный контекст)
Стало: Developer видит только свою задачу + интерфейсы для интеграции
```

**Результат:** 10x меньше контекста → быстрее обработка → дешевле.

#### 3.2 Асинхронная обработка вопросов

**Problem:** Developer спрашивает → блокируется → ждет ответа → продолжает.

**Solution:** Developer спрашивает → ПРОДОЛЖАЕТ РАБОТУ → ответ приходит асинхронно.
```
Было: Developer спрашивает → БЛОКИРУЕТСЯ на Dev-Lead → ждет ответа → потеря времени
Стало: Developer спрашивает → ASYNC QUEUE → продолжает работу → ответ когда нужно
```

**Результат:** Developer не теряет время на ожидание.

#### 3.3 Инкрементальная интеграция

**Problem:** Orchestrator ждет всех Developer'ов → потом начинает интеграцию.

**Solution:** Интегрируй ПО МЕРЕ готовности каждого Developer.
```
Было: Dev1 ✓ ✓ ✓ (ждет), Dev2 ✓ ✓ ✓ (ждет), Dev3 ✓ ✓ ... (работает)
Стало: Dev1 ✓ ✓ ✓ → ИНТЕГРИРУЙ, Dev2 ✓ ✓ ✓ → ИНТЕГРИРУЙ, Dev3 ✓ ✓ ... (работает)
```

**Результат:** Интеграция идет параллельно разработке → экономия времени.

## FAQ

### Сколько времени занимает разработка?
Зависит от сложности:
- Простое приложение (3-5 экранов): 2-3 часа
- Среднее приложение (5-10 экранов): 4-6 часов
- Сложное приложение (10+ экранов, много логики): 8+ часов

### Можно ли менять требования во время разработки?
Да, но лучше на ранних этапах (при Analyzer или Architect). На этапе разработки изменения будут требовать переделки.

### Как развернуть результат на реальное устройство?
Плагин выдает исходный код. Для развертывания:
- **iOS**: используй Xcode, запусти на симуляторе или девайсе
- **Android**: используй Android Studio, запусти на эмуляторе или девайсе
- **Flutter**: используй `flutter run` команду

### Есть ли гарантия что код будет работать?
Плагин следует best practices и проводит все стандартные проверки. Однако, это AI-сгенерированный код, поэтому рекомендуется дополнительное тестирование на реальных устройствах.

### Могу ли я использовать код в коммерческом проекте?
Зависит от твоих лицензий и требований. Код сгенерирован специально для тебя.
